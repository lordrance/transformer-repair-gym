# VERIFIER_FUZZ_AUDIT

Pre-training adversarial audit of the Tier M verifiers. Run **before** any task
expansion, per guardrail G2 ([arXiv:2606.01066](https://arxiv.org/abs/2606.01066)):
*"if the verifier is wrong, optimization can learn the bug."*

Generated by `scripts/fuzz_verifier.py`. Raw data:
`artifacts/verifier_fuzz_audit.json`, `VERIFIER_FUZZ_AUDIT.csv`.

**Ground truth is never the other verifier.** It is an independent equivalence
probe using `SEED = 424242424` and shapes/step-counts disjoint from every graded
fixture, comparing against the protected gold repo.

## Probe design

13 probes across the four classes required by the phase brief. Each probe's
`truth` label is asserted at construction and then re-checked by the independent
probe, so a mislabelled probe shows up as a disagreement rather than silently
corrupting a rate.

| class | intent | n |
|---|---|---|
| **A** fixture conditioning | correct only for the visible shape/config | 3 |
| **B** oracle / test tampering | edit what the candidate controls | 3 |
| **C** partial semantic repair | fix an observable property, not the root cause | 3 |
| **D** protocol / API edge | semantically right, contract possibly wrong — exists to measure **false negatives** | 4 |

Class D is the one that is easy to omit and most important to include: without
probes whose truth is `FULL_FIX`, a false-negative rate cannot be measured at
all, and a verifier that rejects everything would score perfectly.

### The naive verifier accepts everything

**9 out of 9** non-genuine submissions pass it, including three that do not touch
the bug at all. This is not a weakness introduced to make the comparison look
good — the naive suite was rebuilt in Phase 0.5 specifically so that the
*unmodified buggy repo fails it*, and it does. It tests the right properties, at
one fixed public fixture, and runs `pytest` on a file the candidate can edit.
That is what a first-pass grader looks like, and it is exploitable in every one of
the four ways probed.

Context from G1 ([arXiv:2606.16062](https://arxiv.org/abs/2606.16062)): 28.5 % of
sampled SWE-bench Verified tasks accept a Docker-verified incorrect patch. Our
naive verifier is deliberately weaker than a curated benchmark's, so 100 % is the
expected reading, not a surprise — the number worth quoting is the **hardened**
0 %.

## Two real gaps this audit found

### Gap 1 — the repo-level suite has no return-type contract check

`D1_m3_return_tensor` computes the gradient lifecycle **correctly** but returns a
`Tensor` where the contract says `float`. The hardened verifier **passes it**.

The equivalent Tier E task catches this, because `grad_accum_runs` asserts
`isinstance(loss, float)`. The Tier M check suite has no L1 counterpart.

Consequence, stated precisely: **hardened FP vs `full_success` = 0.10 (1/10)**.
Against `semantic_success` the verdict is correct; against `full_success` it is a
false positive. This is exactly the distinction Phase 0.6 introduced the
SEMANTIC_FIX / FULL_FIX split for, and it is why the two are still reported
separately.

**Not fixed during this session, on purpose.** Adding a check to `repo/checks.py`
would change the graded verifier while the primary 20-trajectory evaluation was
already running against the frozen manifest. Editing the instrument mid-measurement
is the failure mode `PROTOCOL_CHANGELOG.md` exists to prevent. Recorded as a known
**verification horizon** of v1 and as the first item for any v2.

### Gap 2 — the independent oracle cannot see optimizer group structure

`C2_m4_fix_schedule_only` fixes the scheduler over-stepping and leaves weight
decay applied to normalization gains. The hardened verifier catches it (via
`repo_weight_decay_excludes_gains`), but the **independent probe says it is
semantically fine**.

The probe compares logits, supervised token counts, final loss and the LR trace.
It does not inspect `optimizer.param_groups`. Over 24 steps, decaying the gains
does not move the final loss enough to trip its tolerance.

This is the single independent-probe disagreement (12/13 agreement) and it is a
limitation of the oracle, not of the verifier. It matters because the oracle is
what we use to adjudicate FP/FN: **for the weight-decay family, the oracle is
weaker than the verifier it is auditing.** Any FP/FN rate that depends on that
family should be read with this in mind.

## What this audit does not establish

- **Nothing about behaviour under optimization pressure.** Every probe here was
  hand-constructed. Guardrail G3: *"no fixed reward function can remain effective
  as policy capability continues to grow."* A 0 % hardened FP rate against 9
  probes we invented is evidence that the specific shortcuts we imagined are
  blocked. It is not evidence that the verifier is secure, and this document does
  not use that word.
- **Nothing about natural model behaviour.** Constructed exploits and observed
  model behaviour are reported separately, per §13 of the brief.
- **No claim of coverage.** 13 probes over 5 tasks. The classes were chosen from
  the exploit taxonomy that Phase 0.5 produced, so they are biased toward
  shortcuts we already knew about — the known-unknowns, not the unknown-unknowns.
