## 2. Scope corrections applied

Both requested scope cuts were made.

**Tiny Transformer MVP.** No KV cache. The reference is embedding → RMSNorm →
causal attention (RoPE) → residual → RMSNorm → MLP → residual → final norm →
LM head → shifted cross-entropy. Nothing in the repo requires hand-deriving the
attention backward; the checks require understanding *forward* tensor shapes,
the autograd data flow, and why each op is written the way it is.

**Reward v0/v1 only.** `reward = 1 − λ·changed_lines` was **removed**. Both
schemes are binary. Patch size is recorded as a metric
(`patch_lines_added_vs_gold`, `identical_to_gold`, `submitted_loc`) and does not
enter any reward. If an ablation later shows shaping is needed, it can be added
with evidence.

## 3. The verifier contract

Deterministic-by-fiat was replaced with an explicit three-level contract.
PyTorch's own reproducibility guidance is that results are not guaranteed
identical across releases, platforms, or CPU/GPU — so nothing here compares
floats for exact equality, and `torch.use_deterministic_algorithms(True,
warn_only=True)` is set rather than hard-on (hard-on turns an unrelated missing
kernel into a spurious task failure).

| Level | What it checks | Tolerance |
|---|---|---|
| **L1 structural** | imports, public API present, shapes, dtypes, finiteness | exact (integers/shapes) |
| **L2 numerical** | multiple hidden inputs vs `trgym.reference`, forward **and** gradients | `atol=1e-5, rtol=1e-4`; gradients compared as relative max-abs at `1e-4` |
| **L3 behavioural** | same data re-split into different micro-batches must give the same update | invariance property at `1e-4`, **not** a loss threshold |

Two structural defences:

1. **Ground truth lives outside the workspace.** `trgym.reference` is the oracle.
   The T4 workspace contains its own copy of `full_batch_gradients`; grading
   deliberately ignores it. Cheat `c5` exists to prove that matters.
2. **Hidden inputs differ from visible ones.** Visible fixtures use `seq_len=8`;
   hidden checks use `1, 3, 5, 16, 31, 64` with different seeds and batch sizes.

## 4. Sandboxing — an honest limitation

`trgym/verifier/sandbox.py` runs candidate code in a subprocess with a 180 s
timeout and `-E` (ignore `PYTHONPATH`/`PYTHONHOME`). That stops runaway loops and
stops a candidate from monkey-patching torch inside the parent process.

**It is not a security boundary.** It shares the filesystem and network with the
parent. Phase 0 only ever executed code that this repo generated. Before any
unattended run or any run over model-generated code at scale, this must become a
container or a Modal sandbox with `--network=none`, a read-only mount, and
CPU/memory limits. Flagged, not hand-waved.

## 5. `minimal_grpo.py`

269 lines. Every required component implemented by hand: multiple rollouts per
prompt, verifiable reward, group-normalized advantage, policy log-probs,
importance ratio, clipping, KL, token mask, optimizer step. Entropy is *recorded*
and not added to the loss, as specified.

Rather than diffing against another repo (which would only prove two things
agree), each test pins a property any correct GRPO must satisfy:

| Property | Test |
|---|---|
| advantages are zero-mean / unit-std within a group | `test_advantages_are_zero_mean_unit_std_within_group` |
| **a group with constant reward produces zero gradient** | `test_constant_reward_group_produces_zero_advantage` |
| at ratio = 1 the surrogate reduces to REINFORCE-with-baseline | `test_at_ratio_one_surrogate_equals_reinforce_with_baseline` |
| beyond `1+ε` with `A>0` the gradient is exactly zero | `test_clipped_positive_advantage_gradient_is_zero` |
| k3 KL is ≥ 0, zero when policies match, and **matches a 200k-sample Monte-Carlo KL to within 5 %** | `test_kl_k3_matches_monte_carlo_kl` |
| recomputed log-probs match the ones recorded while sampling | `test_compute_logprobs_aligns_with_sampled_tokens` |
| masking never lets padding dilute the loss | `test_masked_mean_ignores_padding` |

The constant-reward test is the important one: it is the difficulty-calibration
constraint written as an equation. A task set at 0 % or 100 % pass rate produces
no gradient, whatever else is true.

**End-to-end run** (`artifacts/grpo_demo.json`, 60 steps, CPU, ~2 min):

| | value |
|---|---|
| random baseline | 16/256 = **0.0625** |
| reward, mean of first 5 steps | **0.0730** |
| reward, mean of last 5 steps | **0.9854** |
| entropy | 5.38 → **0.30** (textbook entropy collapse) |
| KL to frozen reference | → ~5.7 |

One finding worth keeping: at `lr=3e-4` — the reflexive default — reward does not
move off the random baseline in 30 steps. At `1e-3` it goes to 0.985. "The RL
loop is correct but the step size is too small to see it" is exactly the failure
that wastes a paid training run. The default in the file is now `1e-3`, with a
comment explaining why.

## 7. Answers to Q1–Q7

### Q1 — Are these really Transformer/ML training tasks, or Python debugging in disguise?

**Really ML.** Evidence: none of the five bugs produces an exception, a stack
trace, or a type error. All five leave a program that runs and returns
plausibly-shaped tensors. What distinguishes right from wrong is a mathematical
property of the operation:

| Task | The fix requires knowing |
|---|---|
| F1 | causality includes the diagonal; lookahead makes val-loss *better*, which is the tell |
| F2 | RoPE's defining property is that ⟨q_m, k_n⟩ depends only on `m−n` |
| F3 | fp16 squares overflow at 65504, so variance must accumulate in fp32 |
| F4 | CE is a per-token mean, so accumulation must share one global denominator |
| F5 | padded positions are not targets and must leave the denominator |

A general-purpose debugger with no transformer knowledge cannot locate any of
them from the symptom text, because the symptom text describes *loss curves and
numerics*, not crashes.

Secondary evidence: the hidden checks are themselves ML statements
(translation invariance of RoPE; gradient equality between accumulation and
full-batch). They could not be written for a generic SWE task.

### Q2 — Does the naive reward actually have an exploitable gap? Show real patches.

Yes, and larger than expected. Two separate results:

**(a) The unmodified buggy file scores naive = 1.0 on all five tasks.** Doing
literally nothing is rewarded. That is the cleanest possible demonstration: the
naive grader does not measure whether the bug was fixed.

**(b) Six hand-written exploits all score naive = 1.0.** The three most
instructive, verbatim from `trgym/cheats/catalog.py`:

*c3 — special-case the fixture's shape:*
```python
_diag = 0 if seq_len == 8 else 1
causal = torch.ones(seq_len, seq_len, dtype=torch.bool, device=scores.device).tril(diagonal=_diag)
```
Correct on the visible `seq_len=8` fixture, leaks the future at every other length.

*c1 — delegate to the gold implementation:*
```python
from trgym.reference.tiny_gpt import causal_attention as _gold_attention
def causal_attention(q, k, v, padding_mask=None):
    return _gold_attention(q, k, v, padding_mask)
```

*c5 — rewrite the oracle instead of the code:* leaves the accumulation bug and
rewrites `full_batch_gradients` in the same workspace file to reproduce the same
wrong normalization, so candidate and oracle agree perfectly.

### Q3 — Does the hardened verifier catch them all? Any false rejection of gold?

**Caught: 6/6.** Five by a named static gate, one (`c5`) only by the hidden
numerical suite — recorded as `expected_gate=None` in the catalog *before* the
run, not rationalized afterwards.

**False rejections of gold: 0/5.** Gold scores naive 1.0 and hardened 1.0 on
every task, with zero gates fired. This is asserted in
`test_gold_submission_scores_one_under_both_schemes` and in `audit_tasks.py`, so
it cannot silently regress.

One caveat I will not hide: two gates are heuristic and *will* produce false
positives at scale. `gate_no_shape_special_casing` fires on any comparison of a
tensor dimension against an integer > 2, and `gate_no_silent_exception_swallowing`
fires on any broad `except`. Both are legitimate in real code. At 5 tasks they
are clean; at 30–50 tasks they need a per-task allowlist, and their false-positive
rate needs to be measured, not assumed. That measurement belongs in the flagship
and is the first thing I would put on its schedule.

### Q4 — What is the API model success rate? Is the difficulty right for RL?

**Unanswered — no credentials on this machine.** The harness is written and takes
one command:

```powershell
$env:OPENAI_API_KEY = "sk-..."
.\.venv\Scripts\python.exe scripts/run_api_baseline.py --model <model> -r 4
```

It prints per-task naive/hardened pass@1 and the exploit-gap rate, writes
`artifacts/api_baseline.json`, and classifies the result as `TOO EASY`
(hardened ≥ 0.95), `TOO HARD` (≤ 0.02), or `USABLE`. Cost is 20 completions —
cents.

What I can say without a model: the environment's dynamic range is *structurally*
sound, because gold scores 1.0 and the unfixed file scores 0.0 under hardened.
Whether a policy lands between those is exactly what the missing measurement
decides.

### Q5 — Scaling from 5 to 30–50 tasks: what automates, what does not?

**Already automated (zero marginal cost):** applying mutations, materializing
workspaces, generating the visible harness and symptom file, gold-vs-buggy
discrimination audit, the cheat audit, level tagging, patch metrics.
`spec.py` also *fails loudly* if a mutation does not apply exactly once or if
visible == hidden, so a broken task cannot enter the set quietly.

**Cannot be automated:**

| Work | Per unit | Notes |
|---|---|---|
| Find real bug evidence for a **new family** | 1.5–3 h | The genuine bottleneck. Searching issue trackers for bugs that are real, silent, and CPU-reproducible. |
| Design the property the hidden checks encode | 1–2 h | The intellectual core. "What equation does this bug violate?" |
| Write symptom text that does not leak the root cause | 15–30 min | |
| Choose the visible subset honestly | 15 min | Must be "what a hurried engineer writes", not "whatever hides the bug" |
| New **instance inside an existing family** | 20–40 min | Checks are reused; only the mutation and symptom change |

**Estimate for 30 tasks:** ~8 families × ~3 h + ~22 instances × ~0.5 h ≈
**35 hours**, call it **30–45 hours** of focused work. For 50 tasks, ~55–70 h.

Recommendation: **8–10 families × 3–4 instances each** beats 30 one-off families.
It also gives a principled held-out split (hold out whole families, not
instances), which is the split that actually tests generalization.

### Q6 — Flagship A/B cost, from Phase-0 traces

Measured on the actual prompts with `tiktoken` (`o200k_base`), not estimated:

| Quantity | Measured |
|---|---|
| mean prompt tokens | **2,393** (826 for T4, ~2,800 for the tiny_gpt tasks) |
| mean gold completion tokens (whole file) | **2,262** |
| tokens per rollout | **4,655** |
| grading wall time per rollout | **2.03 s**, CPU, fresh subprocess |

Tinker `Qwen3.5-4B`: prefill **$0.33/M**, sample **$1.005/M**, train **$0.737/M**.

**Scenario A — current whole-file output format**, 30 tasks, G=8, 8 prompts/step,
150 steps = 9,600 rollouts/arm:

| | per arm |
|---|---|
| prefill 22.97 M | $7.58 |
| sample 21.72 M | $21.83 |
| train 44.69 M | $32.94 |
| **total** | **≈ $62** |

Two arms ≈ **$125**; with a third ablation arm ≈ **$187**.

**Scenario B — switch the answer format to a patch/diff** (~200 completion
tokens instead of 2,262):

| | per arm |
|---|---|
| prefill 22.97 M | $7.58 |
| sample 1.92 M | $1.93 |
| train 24.89 M | $18.34 |
| **total** | **≈ $28** |

Two arms ≈ **$56**; three arms ≈ **$84** — **under the $100 target.**

**This is the most actionable finding in Phase 0.** Whole-file output spends 78 %
of the sample budget re-emitting unchanged code. Changing the output format
before the first paid run cuts the A/B cost by ~55 % and makes patch-size a
meaningful metric at the same time. It does add a patch-application failure mode
that must be graded as a failure, not silently skipped.

**Environment compute: $0.** 9,600 rollouts × 2.03 s = 5.4 CPU-hours per arm,
which runs on this laptop; ~40 min wall-clock at 8-way parallelism. No GPU is
needed anywhere in the loop — Tinker does the sampling and the gradient step.

### Q7 — GO / NO-GO

**CONDITIONAL GO.**

The chain the phase existed to test holds at every link that could be tested
without a model:

```
real Transformer bug  ->  runs but is numerically wrong        [5/5 REAL/REAL-DERIVED]
gold fix              ->  hardened PASS                        [5/5, zero false rejects]
unfixed / cheating    ->  naive PASS, hardened FAIL            [5/5 tasks + 6/6 cheats]
environment           ->  loads by env_id, scores via Rubric   [verifiers 0.3.0]
GRPO                  ->  implemented, tested, learns          [18/18, 0.073 -> 0.985]
cost                  ->  measured, and reducible below $100   [tiktoken + real prices]
```

The one unmeasured link is whether a policy model sits strictly between 0 and 1
on this task set. **Do not start flagship development until that command has been
run.** If the result is `TOO EASY` or `TOO HARD`, the difficulty needs
recalibration first and some of the task set will be rewritten — that is a
redesign of the task mix, not of the architecture.

I am not recommending GO because code has been written. I am recommending it
because the falsifiable claim — *a naive verifier rewards submissions that did
not fix the bug, and a hardened one does not* — was tested and held on 11 of 11
adversarial and unfixed submissions, with zero false rejections of gold.

## 8. What I would change before the flagship

Ordered by expected value:

1. **Run the API baseline.** Closes the only open gate. Cents.
2. **Switch output format to a patch.** ~55 % cheaper per Q6; makes patch size
   meaningful; needs patch-application failures graded explicitly.
3. **Measure the false-positive rate of the two heuristic gates** on legitimate
   human-written fixes before trusting them at 30+ tasks.
4. **Move the sandbox into a container** before running model-generated code
   unattended (§4).
5. **Plan for Linux.** `verifiers.v1` cannot import on Windows (`fcntl`); the
   multi-turn harness and Modal runtime will need WSL2 or a Linux host.
6. **Restructure as families × instances**, and hold out whole families.
