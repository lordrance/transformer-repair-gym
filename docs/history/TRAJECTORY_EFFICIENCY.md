# TRAJECTORY_EFFICIENCY

Guardrail G7 / RQ4. The question is not how good the model is. It is:

> do harder tasks require more **investigation**, or merely more **tokens**?

Those look the same in a cost report and mean opposite things for environment
design. Generated by `scripts/trajectory_efficiency.py` from the raw episode logs.

---

## Aggregate, by tier (`deepseek-v4-flash`, 14-turn budget)

| | Tier M | Tier H |
|---|---|---|
| trajectories | 20 | 20 |
| FULL_FIX | 18 (90 %) | 8 (40 %) |
| mean turns used | 14.0 | 14.0 |
| mean `read_file` + `list_files` | 10.4 | 10.5 |
| mean distinct files read | 9.4 | 9.4 |
| mean `run_command` | 2.2 | 2.2 |
| mean `apply_patch` | 1.33 | 1.15 |
| failed patches | **0** | 3 |
| unusable turns (`noop`) | **0** | 5 |
| ran a training command | 90 % | 90 % |
| ran the visible tests | 65 % | 65 % |
| **submitted voluntarily** | **1/20 (5 %)** | **0/20 (0 %)** |
| **ended by budget exhaustion** | **19/20 (95 %)** | **20/20 (100 %)** |
| prompt tokens / turn | 6,888 | 7,100 |
| cost / trajectory | $0.0158 | $0.0192 |

## Finding 1 — the harder tier costs 21 % more and investigates identically

Tier H halves the success rate (90 % → 40 %) while the trajectory shape barely
moves: same 14 turns, same ~10.5 reads, same ~9.4 distinct files, same 2.2
commands, 3 % more prompt tokens per turn.

So the extra difficulty is **not** being paid for with extra investigation. The
model already reads essentially the whole package on the easy tier; there is no
headroom left to spend. What changes at Tier H is only whether the fix it lands on
is complete.

Read against G7: the token growth from Tier M to Tier H is 21 % — real, but small.
The horizon cost of this environment is dominated by the *fixed* per-episode
context, not by difficulty.

## Finding 2 — trajectory shape carries almost no signal about outcome

Tier H, grouped by the independent label:

| label | n | reads | runs | patches | distinct files | first patch turn | prompt tokens |
|---|---|---|---|---|---|---|---|
| FULL_FIX | 8 | 10.5 | 1.88 | **1.5** | 9.5 | 13.1 | 100,090 |
| PARTIAL_FIX | 4 | 10.5 | 2.0 | **1.5** | 9.0 | 13.3 | 102,476 |
| WRONG | 8 | 10.5 | 2.5 | **0.5** | 9.5 | 13.7 | 97,176 |

Reads are **identical to one decimal place** across all three outcomes. Distinct
files, first-patch turn and token count are within noise of each other. Tier M
shows the same thing: FULL_FIX 10.44 reads vs PARTIAL_FIX 10.50.

**The only discriminator is whether a patch was written at all** — WRONG episodes
average 0.5 patches, meaning half of them never edited anything across 14 turns.

This is a negative result for the obvious hypothesis. One might expect successful
episodes to look more targeted: fewer reads, earlier localization, fewer commands.
They do not. At this scale the model's strategy is **exhaustive enumeration**, not
hypothesis-driven search: read nearly every module, then either commit to a fix or
do not.

Two consequences:
- Trajectory metrics cannot be used as a cheap proxy for reward here. A process
  reward built on "did it investigate properly" would be uninformative.
- The 8-module package is small enough to read exhaustively inside the budget. To
  make localization itself the bottleneck, the repository has to be large enough
  that reading everything is not an option — that is a *scale* change, not a
  difficulty-of-bug change.

## Finding 3 — the model essentially never stops on its own

**39 of 40 episodes ended because the turn budget ran out**, not because the model
judged itself finished. On Tier H it is 20 of 20.

Grading always runs on the final workspace state, so this does not invalidate any
result. But it does mean:

- The 14-turn budget, not the model's own confidence, is the binding constraint.
- We do not know what a larger budget would buy. It is entirely possible that some
  Tier H failures are budget-limited rather than capability-limited, and this
  session cannot distinguish those.
- Reported "difficulty" is therefore difficulty **at a 14-turn budget**, and that
  qualifier belongs on every difficulty number in this project.

`deepseek-v4-pro` submitted 3/10 times — three times the rate of flash, on the same
tasks. Weak evidence (n=10) that voluntary stopping is a model property rather than
a harness artifact.

## Finding 4 — the protocol fix held, and Tier H stressed it

Tier M after the R1b headerless-diff fix: **0 failed patches, 0 unusable turns**
across 20 episodes. The protocol was not the bottleneck.

Tier H: 3 failed patches and 5 unusable turns out of 20 episodes. Small but
non-zero, and it appears only on the harder tier — consistent with the model
producing larger, more speculative multi-hunk edits when it is less sure. Recorded
as PROTOCOL_FAILURE, not CAPABILITY_FAILURE; it affects 8 of 280 total turns.

## Finding 5 — tool selection is stable and sensible

| command | Tier M | Tier H |
|---|---|---|
| `run_training_short` | 16 | 12 |
| `run_visible_tests` | 15 | 17 |
| `run_training` | 8 | 8 |
| `run_training_json` | 5 | 6 |

90 % of episodes ran some training command, on both tiers, including on tasks where
the bug is visible in a forward pass. The model does use the executable environment
rather than only reading — which is the capability that separates this from a
static benchmark, and the main justification for the multi-turn harness existing.

## Limitations

- n = 20 per tier, one model for the tier comparison. Every rate here is coarse.
- The 14-turn budget is a confound for every difficulty claim (Finding 3).
- Only `deepseek-v4-flash` has both tiers; the pro run covers Tier M only, so the
  tier comparison is single-model.
