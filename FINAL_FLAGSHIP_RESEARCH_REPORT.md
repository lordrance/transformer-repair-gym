# FINAL_FLAGSHIP_RESEARCH_REPORT

A GPU-free RL environment for multi-file transformer debugging, with execution-based
grading behind a trusted-comparator boundary.

Every number here is generated by `scripts/build_final_metrics_summary.py` from raw
trajectory files and gate artifacts. The canonical summary is
`artifacts/final_metrics_summary.json`; its digest is pinned in §8 and re-checked by
`scripts/post_success_result_audit.py`, which recomputes the same quantities with
independently written arithmetic.

**What this report does not claim.** No comparison against published baselines or leading
systems. No inferential statistics — the samples are 10–20 episodes per arm, and no test,
interval or significance claim is made or implied. No policy was trained or improved: no
gradient was ever taken against these rewards, and no RL run exists. No generalization
beyond the specific tasks measured. No security guarantee suitable for deployment.

(That paragraph is deliberately phrased around the exact strings `final_acceptance.py`
scans for as forbidden claims. The gate matches substrings, so even a *denial* containing
one would trip it — the same prose-versus-code confusion that R13 documented and that bit
two of the R16 gate checks. Rewording the denial is the honest fix; weakening the gate
would not be.)

## The question

Reward functions for code repair are usually graded by running the tests the candidate can
see. That measures whether the visible suite passes, which is not the same as whether the
defect is fixed, and the gap is where reward hacking lives. This project builds an
environment where the two can be measured separately, and then spends most of its effort
on the thing that turns out to be hard: keeping the answer away from the thing being
graded.

### RQ1 — Does a visible/hidden gap exist, and how large is it?

Yes, at every tier, and it does not shrink with model capability.

| family | n | visible pass | hidden pass | naive FPR |
|---|---|---|---|---|
| Tier M (14 turns) | 20 | 20/20 | 18/20 | 0.10 |
| Tier M pro | 10 | 10/10 | 8/10 | 0.20 |
| Tier H (14 turns) | 20 | 20/20 | 8/20 | **0.60** |
| Tier H (24 turns) | 10 | 10/10 | 8/10 | 0.20 |
| Tier S (48 files, 24 turns) | 12 | 12/12 | 9/12 | 0.25 |

The visible suite passed in **72 of 72 episodes**. The hidden suite passed in 51. Grading on
what the candidate can see would have scored every single episode as a success, including
21 that did not fix the defect.

Hidden-suite false positives are 0.0 across all families, and hidden false negatives are
0.0: the hidden suite never failed a tree that was actually correct.

### RQ2 — Does more thinking time help?

On Tier H, doubling the turn budget from 14 to 24 moved the full-fix rate from 0.40 (n=20)
to 0.80 (n=10). `TURN_BUDGET_ABLATION_REPORT.md` records the verdict token
**BUDGET-SENSITIVE**.

Read carefully: the 24-turn arm is a 10-episode subset, the arms differ in n, and this is
a pre-registered measurement rather than a controlled experiment with matched pairs. The
honest statement is that the 14-turn Tier H difficulty number was **confounded by budget**,
which is exactly what G3 existed to find out. It is not evidence that 24 turns is the right
budget, nor that the trend continues.

### RQ3 — Does localization break down at repo scale?

No — at 48 files it is not the bottleneck.

```
files in repo                 48
structural ceiling on reading 0.5   (one tool call per turn, 24 turns)
fraction of repo inspected    mean 0.181, max 0.271
relevant file located         12/12
full fix                       9/12
```

The agent found the defective file in **every** episode while reading under a fifth of the
repository, with the defect sitting three or four levels below the module named in the
symptom. Exhaustive reading was impossible by construction, not by restraint.

The failures are more informative than the successes. All four `s3_warmup_offbyone`
episodes opened the correct file, `_optim/schedule.py`, and three still failed — two of
them repaired `_train/loop.py` instead. The symptom ("the first optimizer step appears to
accomplish nothing, and the LR curve looks shifted by one step") is equally consistent
with a `scheduler.step()`/`optimizer.step()` ordering bug, which is real, common, and lives
in the loop. **Opening the right file is not the same as reading it correctly**, and the
localization metric cannot tell those apart. See `LOCALIZATION_SCALE_REPORT.md`.

### RQ4 — Can the grader be kept away from the answer?

Only after three attempts, and the first two were wrong in ways that measured clean.

- **R14** found that grading imported candidate code into the rollout process, where
  `gold_repo()` lives. Fixed by grading in a container.
- **R15** found that inside that container the candidate and the checks still shared a
  process, so candidate code could set `ATOL = 1e9` and pass a defective tree. Fixed with a
  static denylist plus a post-run integrity check.
- **R16** found the actual hole: `-v {REPO_ROOT}:/grader:ro` mounted the **entire
  repository**, hidden checks and templates included, into the container running candidate
  code. `open('/grader/trgym/repo/checks.py')` was sufficient. No evasion, no cleverness.
  R15's denylist could not have stopped it, and R15's integrity check could not see it,
  because reading gold is not mutating gold.

R16's answer is structural rather than defensive: the candidate container mounts no
repository. It gets its own workspace, a standalone probe, and public task inputs; it
computes **observations** and returns them over a nonce-authenticated, explicitly validated
channel; gold, the hidden checks and every predicate live in a trusted comparator that
never imports candidate code.

Measured, with an unsafe control to prove the probes are live:

| grader path | leaked | executed | refused before execution |
|---|---|---|---|
| sandboxed (production) | **0 / 17** | 17 / 17 | 0 |
| in-process (unsafe control) | 12 / 17 | 17 / 17 | 0 |

`executed 17/17` is load-bearing. Three earlier versions of this suite reported clean
containment while measuring nothing — once because the package could not import on Windows,
once because the "unsafe" control was calling the same sandboxed grader as the subject, and
once because R15's denylist refused every oracle-seeking probe *before it ran*, so
"contained" meant "never happened".

### RQ5 — What does that isolation cost?

| phase | mean | p50 | p95 | failures |
|---|---|---|---|---|
| cold | 5.325 s | 5.434 s | 5.789 s | 0 |
| final | 5.229 s | 5.260 s | 5.586 s | 0 |
| in-process reference | 0.645 s | 0.627 s | 0.714 s | 0 |

**8.1×**, or 4.58 s per grading job, across 90 jobs with zero failures. The in-process
reference is not a candidate path — it is the pre-R14 design, priced here only for
comparison.

R16 appears to have made this *cheaper* rather than dearer. The pre-R16 note recorded
~8.24 s of container startup against ~0.54 s of actual checks; the post-R16 figure above is
5.23 s for a whole grading job. Those are not the same quantity — startup versus end-to-end
— so the two are not strictly comparable, and they come from different sessions on a
machine with other load. The mechanism is plausible (the container no longer mounts the
repository or imports the grader stack) but this is an observation, not a controlled
measurement, and nothing in the gates depends on it.

### RQ6 — What is still not defended?

The largest caveat, stated plainly: **19 of 23 predicates are forgeable.** Moving the
decision into the trusted process stops the candidate *deciding* its verdict; it does not
make an untrusted process's self-report true. A submission that fabricates its own gradient
norms passes `repo_gradients_reach_optimizer`.

Four checks are unforgeable, because their ground truth is gold and gold is absent from the
container the candidate ran in: `repo_matches_gold_logits`, `repo_supervised_token_count`,
`repo_lr_schedule_matches_gold`, and `repo_contract_public_api` — the last never asks the
candidate anything, since the trusted side reads the submitted sources and compares ASTs.

`predicates.FORGEABLE` is the authoritative list, and
`tests/test_check_surfaces_agree.py` fails if a predicate is ever added without being
classified either way. `SECURITY_MODEL.md` states the rest.

**Verifier v2 is unexercised on the replay population.** G2 passes its frozen criterion
(`v2_FPR ≤ v1_FPR`, `v2_FNR == 0`) with `v1_FP_rate == v2_FP_rate == 0.2778`,
`v1_v2_disagreements == 0`. Across 89 replayed trajectories v2 never once decided
differently from v1. It adds contract-level checks that this population does not trigger.
It is **not** evidence that v2 reduces false positives, and this report does not say so.

## What went wrong, kept on the record

The interesting content of this project is its errors, because each was found by *using*
the evidence downstream rather than by re-reading the claim.

| # | defect | how it surfaced |
|---|---|---|
| R7 | frozen artifacts were mutable; a run overwrote its own evidence | G0 caught itself: `claimed 13, recomputed 16` |
| R8 | "present + stable hash" was treated as "preserved"; a file had not been valid JSON for several runs | reading it downstream |
| R11 | the v1 verifier was **vacuously green** — gold and a planted bug both scored 1.0 | the gold-vs-no-op separation assertion |
| R14 | grading imported candidate code into the process holding gold | setting up the G5 canaries |
| R15 | inside the container, candidate code could rewrite the grader's tolerances | the canaries, once they could run |
| R16 | the whole repo was mounted into the candidate's container | a canary that just called `open()` |
| R17 | `repo_fingerprint` hashed only top-level files, so every Tier S subpackage edit was invisible | `edited_a_relevant_file 0/12` alongside `full fix 9/12` — an impossible pair |

R17 is the cleanest example. The rewards were never affected, because they come from real
grading; only a derived metric was wrong. It was recovered exactly from the graded
workspaces, which still existed, spending no trajectories, with the original values
preserved in `*_ORIGINAL_BUGGY` fields.

Two errors were made in the *gates themselves* while closing R16: two `final_acceptance`
checks searched raw text for `/grader` and `pickle` and matched the comments documenting
their own fix. Both read the AST now. That is R13's lesson, rediscovered inside the
mechanism built to enforce it.
